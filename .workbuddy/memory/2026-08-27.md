# 2026-08-27

## 新增：游玩时 BAD/POOR 判定震动反馈

为 beatoraja-Android 增加了游玩中 BAD(判定值3)/POOR(判定值4) 时的震动反馈。

- 触发点：`core/.../play/JudgeManager.java` 的 `updateMicro(...)`，新增私有方法 `vibrateOnBadOrPoor(judge)`。
- 实现方式：core 通过 libGDX 平台接口 `Gdx.input.vibrate(ms)` 触发（符合架构：core 不直接依赖 Android SDK）。
  - BAD=25ms，POOR=45ms；节流 45ms 防止连打叠加；autoplay 与 MISS(5) 不触发。
- 配置开关：`Config.vibrationOnBad`（默认 true），并接入 `SettingsActivity`（新增 Switch + 字符串 `vibration_on_bad`），`saveConfigToJson` 为合并写所以新字段不会被丢弃。
- 权限：`android/AndroidManifest.xml` 增加 `android.permission.VIBRATE`（normal 权限，无需运行时申请）。
- 注意：`updateMicro` 可能在判定线程（1000Hz）调用，`Gdx.input.vibrate` 仅调用系统 Vibrator，线程安全；已用 `Gdx.input == null` 守卫测试/headless 场景。

## 修订：震动支持手柄（精确版：有手柄震手柄，否则震手机）

- 用户要求：连手柄时震手柄、没手柄时震手机（精确版），且不希望改动 core。
- 做法：在 android 模块新增 `GamepadAwareAndroidInput extends DefaultAndroidInput`，覆写 `vibrate(int)`，内部用 `InputDevice.getDeviceIds()` 扫描 GAMEPAD/JOYSTICK 源且 `getVibrator().hasVibrator()` 的设备，找到就 `VibrationEffect.createOneShot`(API26+)/`vibrate(ms)` 震手柄并返回；否则 `super.vibrate(ms)` 震手机。
- 接线：`AndroidLauncher` 覆写 `createInput(Application, Context, Object, AndroidApplicationConfiguration)` 返回 `new GamepadAwareAndroidInput(...)`，从而让 core 既有的 `Gdx.input.vibrate(ms)` 自动走精确版——core 零改动。
- 依据：libGDX 1.14.0 的 `AndroidApplication.createInput` 为 public 工厂方法，默认 `new DefaultAndroidInput(this,this,graphics.view,config)`；`DefaultAndroidInput` 的 `vibrate(int)` 委托给内部 `haptics`。签名已用 WebFetch 核对 1.14.0 源码确认。
- 前提：`android.permission.VIBRATE` 已存在；手柄振动同样依赖该权限。minSdk>=21 满足 `InputDevice.getVibrator()`(API16)。android 模块编译通过。
- 注意：`InputDevice` 扫描每次判定都会跑（被 JudgeManager 的 45ms 节流限制频率），开销极小；个别手机可能把自身枚举为带 JOYSTICK 源的 InputDevice，此时会震其自身马达（=手机），无害。

## BUG 修复：扫描按钮闪退（NPE: Gdx.files.absolute on null）

- 现象：设置页点「扫描」直接崩溃，`NullPointerException` at `Config.read`→`Gdx.files.absolute`（Gdx.files 为 null）。
- 根因：① `SettingsActivity` 是 AndroidManifest 里的 **LAUNCHER 入口**，先于游戏启动；`MainLoader.setSongDatabaseAccessor()` 只在 `AndroidLauncher.onCreate` 调用，故设置页此时 `songdb` 为 null。② `MainLoader.getScoreDatabaseAccessor()` 的 `if(songdb==null)` 分支调 `Config.read()`（依赖 Gdx.files），在 Gdx 未初始化时直接 NPE——且这分支读出的 config 从未被使用，是桌面遗留死代码。`scanSingleFolder` 里的 null 守卫因方法已先崩而永远到不了。
- 修复：
  - `core/MainLoader.java`：把 `getScoreDatabaseAccessor()` 简化为直接 `return songdb;`，删掉会崩的 `Config.read()` 回退分支。
  - `SettingsActivity.scanSingleFolder`：改为先调新助手 `resolveSongDatabaseAccessor()`；`songdb` 为空时直接在 Android 侧 `new AndroidSQLiteSongDatabaseAccessor(this, getFilesDir()+"/songdata.db", bmsPaths)` 并 `setSongDatabaseAccessor`，使未进过游戏的用户也能扫描。构造函数仅依赖 Context+SQLite，不依赖 Gdx。
- 教训：Android 的 LAUNCHER 是 SettingsActivity 而非游戏；任何"取游戏内单例"的逻辑在设置页都可能是 null，必须做 Android 侧降级构造或显式 null 守卫。
- :core 与 :android 均编译通过（仅 deprecation 提示）。

## 新增：设置页加 bms 路径后，进游戏立即可见 + 游戏内手动刷新

- 用户新方案（替代已撤销的"设置页扫描"）：在设置页添加歌曲目录 → 进游戏后路径作为 [root] 子项显示（"songs 0"）→ 在游戏内手动刷新扫描。这是更安全的做法：扫描只在 Gdx 已初始化的游戏内跑。
- 数据链路已天然贯通：SettingsActivity、AndroidLauncher、Config.read() 三者都读写同一个外部 `config_sys.json` 的 `bmsroot` 数组（AndroidLauncher 设 `beatoraja.root=getExternalFilesDir`，与 SettingsActivity 同目录）。
- 缺口：新加的 bmsroot 在未被扫描过之前不会出现在列表里（folder 表记录是扫描时由 `insertFolder` 写入的）。已补：
  - `AndroidSQLiteSongDatabaseAccessor.registerBmsRootFolders()`：仅把当前 `bmsroot` 目录写进 folder 表（parent=ROOT_CRC，与 FolderBar 按 `parent=ROOT_CRC` 查 [root] 子项一致），不扫描歌曲。用 `new FileHandle(new File(...))` 构造，**不依赖 Gdx.files**，因此可在 `AndroidLauncher.onCreate` 里 `initialize()` 之前安全调用（避免之前设置页扫描的 NPE 陷阱）。
  - `AndroidLauncher` 在创建 accessor 后、`initialize()` 之前调用 `androidAccessor.registerBmsRootFolders()`。
- 游戏内手动刷新本来就存在：FloatingMenu 的 "Update Song" 按钮（keycode F2）→ `KeyBoardInputProcesseor.F2(11,Keys.F2)` 默认绑定 `KeyCommand.UPDATE_FOLDER` → `MusicSelectInputProcessor` 触发 `executeEvent(update_folder)` → `main.updateSong(null)` 全量扫描全部 bmsroot 并刷新选曲。无需新增刷新按钮。
- 注意：默认 `Config.updatesong=false`（启动不自动扫描），所以进游戏后需手动点 "Update Song" 刷新——正好符合用户期望的"手动刷新"流程。若想要启动自动扫描，可在设置页开 "Scan Songs On Launch"（updatesong）。
- :android 模块 `compileDebugJavaWithJavac` 通过（仅 deprecation 提示）。

## 光敏性癫痫警告弹窗（最终方案：在 SettingsActivity 点击"开始游戏"时弹出）

- 演变：最初放在 `AndroidLauncher.onCreate`（进入游戏自动弹），后因与 libGDX 初始化并发易闪退，且用户希望"点开始游戏才弹、点我已知晓才进游戏"，最终迁移到 `SettingsActivity`。
- 最终实现：
  - `SettingsActivity` 的"开始游戏"按钮（`R.id.saveButton`，点击时先 `saveConfigToJson()`）调用 `launchGame()`。
  - `launchGame()` → `showPhotosensitiveWarningThenLaunch()` 弹原生 `AlertDialog`（标题/正文/按钮按**系统语言**）。
  - 点 `epilepsy_warning_close`（中文"我已知晓"）按钮回调 `startGameActivity()` → `cleanupResources()` + `startActivity(AndroidLauncher)` + `finish()`，才真正进入游戏。
  - `setCancelable(false)`：只能点按钮关，点外部/返回关不掉。
- 系统语言取值：`Resources.getSystem().getConfiguration()` 取系统 locale + `createConfigurationContext(sysConfig)` 仅用于 `sysCtx.getText(R.string...)`，使文案不受 `applyLanguage` 影响；`Builder` 必须用 `this`（Activity）作上下文（用 sysCtx 当 Builder 不渲染）。
- `AndroidLauncher` 内警告逻辑已全部移除（`showPhotosensitiveWarning` 方法及 `photosensitiveDialog` 字段删除）。
- 文案 key：`epilepsy_warning_title` / `epilepsy_warning_message` / `epilepsy_warning_close`，4 语言（en/zh/ja/ko）。
- 坑（仍适用）：Gradle `packageDebugResources` 在 Windows 上偶发 "Failed to delete ...\merged.dir\values-zh" 增量缓存错误（非代码问题），删掉 `android/build/intermediates/incremental/debug/packageDebugResources/merged.dir` 后重跑即通过。
- :android 模块 `compileDebugJavaWithJavac` 通过（仅 deprecation 提示）。
- 经验：游戏 Activity 内弹系统级提示，**务必延后到 Gdx 初始化完成之后**，并提升窗口层级/不抢焦点，否则既易与渲染线程冲突，又易被 SurfaceView 盖住。
  - 后续迭代：① 关闭时长 3s→5s，**后去掉自动关闭**（已有手动关闭按钮，无需定时）。② 加关闭按钮：新增多语言 `epilepsy_warning_close`（英 I Understand / 中 我已知晓 / 日 理解しました / 韩 확인했습니다），Builder 加 `setPositiveButton(closeText, (d,w)->{ photosensitiveDialog=null; d.dismiss(); })`；仍保留 `setCancelable(false)`（仅按钮可关，点外部/返回键不关）。已删除 `postDelayed` 自动关闭计时器。
