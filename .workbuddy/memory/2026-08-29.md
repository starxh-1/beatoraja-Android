## 调查：BMS 音频时长（tail）探测漏掉子目录音频 —— 已定位根因（未改代码）

### 现象
某谱面有 `audio/bgm.ogg`（2 分钟），播放正常但 play 界面时长不对。并非所有 ogg 谱面都复现。

### 根因（已确认）
时长探测与音频播放用了**两套不同的路径解析**，子目录下必然 miss：

- **播放**（`AbstractAudioDriver.java:377`）：
  `File rawPath = new File(dpath, wavlist[wavid]); FileHandle[] paths = AudioDriver.getPaths(rawPath.getPath());`
  → 正确拼接相对路径，子目录 `audio/bgm.ogg` 能命中。
- **测时长**（`BMSPlayer.java:260-300` 与 `MusicPlayer.java:820-860`，两处同构）：
  ```java
  dirFiles = bmsDir.listFiles();                       // 不递归
  fileCacheMap.put(f.getName().toLowerCase(), f);      // key 只有文件名
  audioFile = fileCacheMap.get(lowerName);             // lowerName = "audio/bgm.ogg" → 永远 null
  ```
  `listFiles()` 只返回 `audio` 这个**目录**本身（key="audio"），查 "audio/bgm.ogg" 和兜底的
  "audio/bgm.{ogg,wav,flac,mp3}" 全都 miss → `audioFile == null` → 整段跳过。
  → `maxTailMs = 0` → `playtime = max(lastEventTime + 1000, lastNoteTime + 0)` → 2 分钟音频尾部被砍。

### 关联逻辑
- `maxTailMs` 来自 DB：`resource.getSongdata().getTail()`，命中缓存时打日志 `Audio tail loaded from database`。
- 非缓存路径算完会写回：`updateSongTail(model.getSHA256(), maxTailMs)`。
- 只有 `<= 0` 才重算，所以**一旦算出非零的错值会被永久缓存**（算成 0 则每次重试，不会固化）。

### 同一段代码里的其他隐患（次要）
1. 启发式跳过假设码率 ≥ 8 bytes/ms（=64kbps）：`if (lastTime + (fileSize/8) <= lastNoteTime + maxTailMs) continue;`
   低于 64kbps 的 ogg 会被误跳过（真实时长 > fileSize/8），tail 偏小。
2. `PCM.tryOggDuration()` 倒序裸扫 "OggS" 找尾页，**不校验页完整性/CRC/serial**，
   payload 里巧合出现 "OggS" 会把后续 8 字节当 granule → 离谱时长，且会被写库缓存。
3. 同函数 216-225 行第一次 OggS 查找是死代码（结果被 228 行覆盖）。
4. `raf.read(head)` 不保证读满 4096 字节，应用 `readFully`。

### 建议修法
时长探测应改用 `AudioDriver.getPaths()`（与播放同一套解析），或把 `fileCacheMap` 改为
**递归扫描子目录、key 用相对路径**（并归一化反斜杠），同时保留 O(1) 查表避免数千次 syscall。

## 修复：libgdx-oboe 音频回退逻辑在 refactor 中被误删（API29 Mokee 无声/重连死循环）

### 现象
API 29 的 Mokee ROM 上日志：
```
OboeAudio W Passing AudioStream pointer deprecated ...
libGDX-Oboe D oboe_engine::resume. State: Open
libGDX-Oboe D oboe_engine::resume. State: Open
libGDX-Oboe D oboe_engine::resume. State: Disconnected
```
流能 Open 但 `requestStart()` 后变成 `Disconnected`，导致 `onErrorAfterClose` 无限重连 AAudio，无声/卡死。

### 根因
`libgdx-oboe` 子模块 commit `fe8918d`（`perf(audio): align oboe_engine with upstream to fix 32-bit frame drops`）的 refactor，把 `connect_to_device()` 里 **AAudio→OpenSL ES 回退 + 熔断机制** 整个删了：
- 旧版：先 `try_open(AAudio)`；失败或断开后 `try_open(OpenSLES)`；并带熔断（1.5s 内重连 ≥3 次 → `m_use_opensl_fallback=true` 强制 OpenSL）。
- 新版：不调 `setAudioApi()`（依赖 Oboe 默认 `Unspecified`）。但 Oboe 的自动回退**只在 `openStream` 失败**时触发；对"打开成功但 start 后断开"无效 → 一直重试 AAudio。

### 修复（保留 32 位性能修复：热路径 `onAudioReady` 仍无锁）
文件：`libgdx-oboe/library/src/cpp/audio/oboe_engine.{hpp,cpp}`
- hpp：加字段 `m_use_opensl_fallback`/`m_consecutive_errors`/`m_last_reconnect_time` + `std::mutex m_stream_mutex`；补 `#include <chrono>` `<mutex>`。
- cpp `connect_to_device()`：恢复熔断计数（1.5s 内 ≥3 次 → 强制 OpenSL）+ `setAudioApi(fallback?OpenSLES:AAudio)` + AAudio 打开失败即回退 OpenSL + 关闭旧流防泄漏 + 回读实际采样率 + 日志。
- `resume/stop/blocking_write/blocking_read` + 析构：改用"加锁取裸指针快照、锁外操作"模式，避免重连时 use-after-free，且不把锁放进 `onAudioReady` 热路径（保留性能修复）。
- 注意：`error()` 在 log.hpp 标了 `[[deprecated]]`，调用仅产生警告，不影响编译（旧代码也这么用）。

### 验证
- 本机无 C++ 编译器（仅 Node/Python 托管运行时），不能在此编译 .so；已逐一对 Oboe 头文件核对所用 API 名称（`AudioApi::AAudio/OpenSLES`、`StreamState::Disconnected`、`Result::ErrorDisconnected`、`convertToText` 模板、`setAudioApi`、`log.hpp` 的 error/warn/info/debug 宏）。
- 需用户用 `./gradlew :android:assembleDebug` 重新编译 native 库验证；预期 Mokee 上 3~4 次快速重连后稳定切到 OpenSL ES，不再死循环。
- `oboe_engine` 公开接口未变，`audio_player.cpp`/`music.cpp` 不受影响。

### 补充
`Passing AudioStream pointer deprecated` 警告来自 libGDX 的 OboeAudio Java/native 层（Oboe 新版 API 弃用提示），与本次断开无关，属良性。

## 修复（第二轮）：第一轮回退没生效 —— 触发点错了 + 标志不是进程级

### 真机复测结果（装 APK 后）
```
Stream opened: API=AAudio, State=Open, OpenSL_fallback=false   ← 打开成功，回退分支没进
AAudioStream_requestStart(s#1) returned -889 / -895 / -899      ← 失败发生在 requestStart
（无 "Previous device disconnected" 日志 → onErrorAfterClose 从未被调用）
... 之后 OboeAudio initialized successfully 再次出现，s#1 → s#2，
第二台 engine 的 OpenSL_fallback 又是 false
```

### 两个根因
1. **触发点错了**：失败发生在 `requestStart()`，而 `openStream()` 是成功的（`State=Open`）。
   Oboe 把该错误**直接返回给调用方，不会触发 `onErrorAfterClose()`**（该回调只在流被 close 时才走）。
   所以只在 `connect_to_device()`/`onErrorAfterClose()` 里做回退 **永远不可能触发**。
   已核对 Oboe 源码：`AudioStreamAAudio::requestStart()` 直接调 `stream_requestStart`，无内部重试。
2. **标志是实例成员**：engine 会被整体销毁重建（`AndroidLauncher` → `OboeAudio` → `audio_player` → `oboe_engine`），
   每次重建 `m_use_opensl_fallback` 都清零，于是反复重试坏掉的 AAudio。

### 修复
文件同上 `oboe_engine.{hpp,cpp}`：
- `m_use_opensl_fallback` → **`static std::atomic<bool> s_opensl_fallback`**（进程级闩锁，跨 engine 重建存活），
  类外定义 `std::atomic<bool> oboe_engine::s_opensl_fallback{false};`（非 inline static，兼容低 C++ 标准）。
- **`resume()` 改为"最多两次"循环**：`requestStart()` 失败 → `s_opensl_fallback.exchange(true)`，
  若旧值为 false（说明当前是 AAudio 首次失败）就 `connect_to_device()` 重建为 OpenSL 再试一次；
  若旧值已为 true（已经在 OpenSL 上还失败）就放弃，避免死循环。
- 并发加固：`std::recursive_mutex m_lifecycle_mutex` 包住 `resume()/stop()/connect_to_device()`，
  防止回退重建 `m_stream.reset()` 时另一线程正持有裸指针（野指针崩溃）；
  用 recursive 是因为 Oboe 可能在 `close()` 内同步回调 `onErrorAfterClose()` 重入；
  另加 `bool m_reconnecting` + `flag_reset` RAII 重入守卫，杜绝嵌套重建。
- 熔断计数保留（1.5s 内 ≥3 次快速重连），命中时也置位全局闩锁。

### 验证（这次真编译了）
本机可在 `E:\Android-SDK\ndk\29.0.14206865` 找到 NDK clang++，直接单独编译 native 文件：
```bash

SYSROOT="E:/Android-SDK/ndk/29.0.14206865/toolchains/llvm/prebuilt/windows-x86_64/sysroot"
D="E:/beatoraja-Android/libgdx-oboe/library"
"$CLANG" --target=aarch64-linux-android29 --sysroot="$SYSROOT" -stdlib=libc++ -std=c++17 \
  -isystem "$SYSROOT/usr/include/c++/v1" \
  -I "$D/dependencies/oboe/include" -I "$D/dependencies/fmt/include" \
  -I "$D/dependencies/frozen_string" -I "$D/dependencies/result" -I "$D/src/cpp" \

```
- `oboe_engine.cpp` 完整目标码编译通过（生成 .o，仅 frozen 库与既有 `error()` 的 deprecation 警告）。
- `audio_player.cpp` 语法检查通过（公开接口未变）。

### 预期行为
首次 `resume()` 时 AAudio 的 `requestStart()` 失败 → 立即重建为 OpenSL ES 并成功启动；
之后本进程内新建的任何 engine 都直接走 OpenSL ES，不再重试 AAudio。
若日志出现 `requestStart() failed on OpenSL ES as well; giving up.` 说明该 ROM 两条路都不通。

## 调查：select 界面 select.ogg 卡死（mp3 正常）

### 现象
select 界面播放 SELECT 音效时，选 select.ogg 会卡死（UI 冻结），选 select.mp3 正常。

### 根因（已确认）
- `SystemSoundManager.play(SELECT)` → `AudioDriver.play(path)`（主/渲染线程同步）→ `getSound()` → `getKeySound(new File(p))` → `PCM.load` → `PCMLoader.loadPCM`。
- `loadPCM` 对 ogg/mp3/flac 统一走 `Gdx.audio.decodeToPCM(path)`（反射调用，PCM.java:526-541）。Android 上 `Gdx.audio`=libGDX `AndroidAudio`，内部用 **MediaCodec** 解码。
- **mp3**：MediaCodec 普遍支持 → 正常。
- **ogg/vorbis**：MediaCodec 支持极差且不可靠，在 API29 Mokee 这类 ROM 上 `dequeueOutputBuffer` 易陷无限等待或解码器创建失败被吞异常 → 解码线程阻塞；该调用**在主线程同步执行** → 整个 select 界面冻结 = 卡死。
- 项目无自带 ogg Java 解码库（grep 无 jorbis/vorbis-java，gradle 无 mp3spi 等），完全依赖平台 MediaCodec。

### 为何游戏内 bgm.ogg 正常
游戏内 BGM/歌曲走 Oboe 流式播放，不经过 `decodeToPCM` 全量解码路径；唯有 `SystemSoundManager` 的 SELECT/DECIDE 一次性全解码到内存，才踩中此坑。

### 修复建议
1. 最快绕过：select 音效改回 `select.wav`（走 WavInputStream 分支，完全不碰 MediaCodec，最稳）或 `select.mp3`（已验证可播）。
2. 治本：`PCM.loadPCM` 对 ogg 改用纯 Java 解码器（jorbis/vorbis-java），跨平台一致且不会卡死；并把首次解码放到后台线程，避免冻结 UI。
3. 验证：logcat 卡死时应停在 `android.media.MediaCodec` / `AndroidAudio.decodeToPCM`。

### 治本实施（已提交 commit `66e5ed4c`，2 文件 +165/-1）
- `core/build.gradle`：`implementation 'org.jcraft:jorbis:0.0.17'`。
  **jogg 类已并入 jorbis-0.0.17.jar**（jar 内同时有 `com/jcraft/jorbis/*` 和 `com/jcraft/jogg/*`），无需单独加 jogg 依赖。
- `PCM.java`：新增 `PCMLoader.decodeOgg(FileHandle)`（jorbis 解 ogg → 16-bit 交错 PCM）+ 内部类 `OggDecodeResult`；
  `loadPCM` 的 ogg 分支改走 jorbis，**mp3/flac 仍走 MediaCodec**（该路径下可靠）。

### 实现中的关键坑（务必记住）
Vorbis 的 3 个 header 包（ID/Comment/Setup）**常分布在不同 Ogg 页中**，解析必须跨多轮文件读取保留状态：
- `os.init/vi.init/vc.init` 只能调用一次（用 `streamInitialized` 标志），且必须用首页 serial；
- 已解析包数用 `headerPackets` 持续累加，取满 3 个才 `synthesis_init/vb.init`；
- 本页包不足时让 `while (os.packetout(op)==1)` 自然结束并 `continue` 回外层读文件取下一页。
初版在等待下一页时**重复 init**，丢掉已解析 header，实测 select.ogg/decide.ogg **全部解码失败**
（抛 "OGG Vorbis header 不完整"）——编译通过不代表逻辑正确，必须实机解码验证。

### jorbis API 要点（javap 核对）
- `DspState.synthesis_pcmout(float[][][], int[])` **返回样本数，数据写入出参**：`pcm[0][ch]` + `index[ch]` 偏移（不是返回值）。
- `Info.channels` / `Info.rate` 是 public 字段；`Block.synthesis(Packet)`、`DspState.synthesis_blockin(Block)`、`synthesis_read(int)`。
- `SyncState.buffer(int)` 返回写入偏移，数据读入 `oy.data[offset..]`，再 `oy.wrote(bytes)`；EOF 时 `oy.wrote(0)` 后继续 pageout 排空。

### 验证手段（可复用）
反射直调私有静态方法 `bms.player.beatoraja.audio.PCM$PCMLoader.decodeOgg(FileHandle)`，
用小测试类读真实文件并反射取 `data/channels/sampleRate`：
select.ogg → 11948344 样本 / 2ch / 44100Hz / 270.94s（非静音）；decide.ogg → 90112 / 2ch / 44100Hz / 2.04s。

## 日志解读：AndroidForwardingOs "Recovering failed rename" / "Rename recovery failed (Fix with AI)"

### 现象
导入 `Download/beatoraja/bgm/<set>` 时出现 E 日志，但导入最后成功：
```
V  Recovering failed rename /storage/emulated/0/Download/beatoraja/bgm/ModernChic
   to /storage/emulated/0/Android/data/com.starxh.beatoraja/files/bgm/ModernChic
E  Rename recovery failed  (Fix with AI)
   java.nio.file.DirectoryNotEmptyException: <源目录>
   at ... AndroidLauncher.ensureExternalResourceImport(AndroidLauncher.java:587)
```

### 原因
- `AndroidLauncher.java:587` 的 `folder.renameTo(destDir)` 把 `Download/...`（共享存储）移入
  `Android/data/<pkg>/files/...`（app 专属）。Android 11+ 二者是**不同 FUSE 挂载点**，
  跨挂载点 rename 必然返回 EXDEV 失败——**不是偶发**。
- Android 11+ 的 `AndroidForwardingOs` 拦截 java.io 文件操作，rename 失败后打 V 日志并
  **自动抢救**：改用 `Files.move` 做 copy+delete。删源时若发现源目录仍非空
  （`UnixCopyFile.ensureEmptyDir`）→ 抛 `DirectoryNotEmptyException`，打 E 日志。
- `Fix with AI` 是 Android 新版系统日志的固定后缀，不是 app 打的，也不是真有 AI 参与。

### 为何最终成功
该异常被 Android 内部吞掉，`renameTo` 只返回 false；beatoraja 在 else 分支
（`AndroidLauncher.java:590-596`）有兜底 `copyDirectory(folder, destDir)` + `deleteRecursive(folder)`，
随后会打 `Copied and deleted bgm folder: <name>`。`copyDirectory` 用
`new FileOutputStream(destChild)`（默认覆盖），即使抢救残留不完整文件也会被完整重写 → 数据完整。

### 结论与可选优化
良性日志噪音，功能正常。但每次导入会「rename 失败 → Android 抢救复制一遍且失败 → 再复制一遍」，
IO 翻倍、导入变慢。可选：`Files.getFileStore(a).equals(getFileStore(b))` 判断是否同卷，
同卷才 rename，跨卷直接 copy+delete，跳过 Android 的抢救。
